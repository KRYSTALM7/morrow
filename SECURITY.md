# Morrow security notes

This document describes the security posture of the Stage 4 application in this repository. It is a code review summary, not a penetration-test result, compliance assessment, or production security certification. Stages 1–3 are separate historical builds and do not inherit changes made to Stage 4.

## Threat model

The service accepts untrusted HTTP requests for wallet, request, authorization, history, assistant proposal, and PayPal checkout operations. Relevant threats include credential guessing, account takeover, cross-user object access, duplicate money operations, malformed or oversized input, malicious browser content, forged payment notifications, replayed provider operations, and disclosure of secrets or financial data through logs. The durable SQLite wallet, finance, and PayPal stores have separate transaction and trust boundaries.

## Existing controls

- Passwords are stored as per-password salts and `scrypt` hashes (`n=2^14`, `r=8`, `p=1`, 32-byte output); hash concurrency is bounded. Login errors do not distinguish an unknown email from a wrong password.
- Authenticated routes resolve the bearer token to a server-side user and scope PayPal checkout reads/captures to the owning user. User IDs in request bodies are not accepted as authorization authority.
- Wallet requests are serialized by SQLite `BEGIN IMMEDIATE` transactions across service processes, with an in-process lock for shared service state. Wallet and finance mutations use idempotency keys where supported. Wallet history, corrections, refunds, holds, and imported state have domain validation and regression coverage.
- Login and signup attempts are throttled by account identifier and remote address in a persistent SQLite table. Login/signup limits use a 15-minute window; passwords are hashed outside the wallet lock.
- Request bodies are capped (2 MB for ordinary requests; 512 MiB for the test import route), JSON nesting is bounded, errors are normalized, and static paths are constrained to the web root.
- Responses include `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. HTML has a restrictive same-origin CSP with `frame-ancestors 'none'`, `base-uri 'none'`, and `form-action 'self'`.
- The app does not enable cross-origin access. Browser bearer tokens are held in `localStorage`; this requires continued XSS prevention and is a material limitation compared with an HttpOnly, Secure, SameSite session cookie.
- PayPal is restricted to HTTPS Sandbox API hosts. OAuth credentials come from environment variables. The service verifies webhook signatures with PayPal, checks event deduplication, validates observed order/capture data, uses stable provider request IDs, scopes checkouts by owner, and writes immutable checkout audit events to SQLite.
- Commitments, occurrences, shared expenses, settlements, idempotency records, and finance audit events are persisted in the versioned SQLite finance schema. Their API derives ownership from the authenticated bearer token, scopes every read and mutation to that owner, resolves participant handles server-side, validates request fields, and returns the same not-found response for absent and non-owned records. Finance writes use a SQLite transaction and owner/operation/key-scoped idempotency records.
- Commitment payments are records against individual occurrences; they do not debit the wallet. Reimbursements are separate append-only manual settlement records; they do not credit the wallet. Outstanding receivables are derived from participant shares minus recorded settlements, so they are not counted as available funds. PayPal checkout is not automatically matched to a reimbursement.
- Wallet users, balances, payments, requests, authorizations/holds, and idempotency records are persisted as a validated versioned snapshot in a separate SQLite database. The snapshot contains no bearer-token map. Session rows contain only SHA-256 token hashes, user IDs, creation/expiry times, and revocation times; presented tokens are hashed before lookup. Login creates a session, logout revokes it, and sessions survive restart until expiry/revocation. Migration v3 extracts sessions from the legacy plaintext map and rewrites the snapshot; migration v4 checkpoints and vacuums the database, then truncates WAL before serving. The separate scrub-completion marker makes startup retry cleanup if interrupted. The application does not create SQLite backups; externally managed backups made before migration may contain old plaintext tokens and must be retired or securely replaced. Protect current database files, WAL files, and backups.
- Forecast and safe-to-spend endpoints require authentication, use the current user's durable wallet statement and owner-scoped commitments, and persist per-user savings targets, safety buffers, and model-versioned forecast snapshots in SQLite. Available funds are sourced from the existing wallet calculation after active holds, which are deducted only once. Forecast responses become explicitly unavailable when three complete prior wallet-history months cannot be established or the statement is incomplete. The ledger has no expense categories or external account feeds; outputs are limited to this wallet and never infer missing categories.
- The existing `/ai/proposals` assistant remains a deterministic parser whose supported actions require server-side confirmation. The read-only `/ai/companion` sends a bounded question and minimum authenticated-user financial summary to Gemini only when configured. It omits transaction descriptions, counterparty IDs, credentials, and other users' records. Gemini has no tools or mutation access. The server rejects generated numeric/currency claims and returns verified figures separately; unavailable Safe-to-Spend stays unavailable. Provider errors use a fallback without upstream details. Requests are limited per user.

## Known limitations and risks

- Bearer sessions expire after 30 days. The database stores token hashes, and logout revokes the presented session. The browser keeps its bearer token in `localStorage`, so XSS remains a material risk.
- The v3 migration scrubs the active wallet SQLite database and its WAL, but cannot erase copies already made by external backup tools, filesystem snapshots, or copied database files. Retire pre-migration backups under your retention policy.
- HTTP access logging includes the request line and may expose sensitive query parameters if a future route puts secrets in a URL. Keep credentials and personal data out of URLs; deploy behind access-controlled, redacting logs.
- The deployment example binds to `0.0.0.0`; TLS termination, trusted proxy policy, production CORS policy, CSRF/session-cookie design, monitoring, backups, and incident response are deployment responsibilities and are not implemented here.
- The large test import body cap is intentionally exceptional and must not be exposed on a public deployment. Test routes are disabled by default; keep the legacy `POCKETFUL_ENABLE_TEST_ROUTES` variable unset outside isolated development.
- Profile/security settings are not implemented. Gemini explanations are optional and require deployment-side provider and privacy review. Finance SQLite tables are durable, and their user identifiers remain application-level references; deleting or resetting wallet users does not automatically clean up finance rows. Safe-to-spend covers only Morrow wallet funds and observed wallet outflows, not a user's full financial position.
- SQLite is the only persistence backend. Cloud Run's local writable filesystem is ephemeral; the current SQLite files must not be placed there as durable state. A durable Cloud Run deployment requires a supported shared database adapter and a tested migration. Process-local statement snapshots, pending assistant proposals, and companion rate counters also need shared storage/coordination before horizontal scaling.
- The wallet payment model has no expense category and does not link commitment occurrences to transactions except by an exact user-supplied payment ID reference. Forecasts therefore return no variable category breakdown and do not guess whether an unlinked transfer paid a commitment.
- Reimbursement entry is a user assertion, not proof of a bank transfer. There is no automated bank feed, matching workflow, or PayPal-to-reimbursement reconciliation endpoint. Commitment payment status is similarly user-recorded and does not verify an external payment.
- PayPal checkout records persist separately from the durable wallet ledger. The current checkout is merchant checkout and does not create a wallet ledger posting or prove an internal P2P transfer.

## Local configuration

Use only PayPal Sandbox application credentials. Set `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, and (for webhooks) `PAYPAL_WEBHOOK_ID` in an ignored local environment file or secret manager. `PAYPAL_BASE_URL` must remain an HTTPS PayPal Sandbox host. Never place real credentials in source, fixtures, screenshots, `room.json`, or logs. `PAYPAL_DB_PATH` should point to a persistent, access-restricted volume when testing checkout persistence; finance tables share it by default. `MORROW_FINANCE_DB_PATH` can select a separate SQLite file. Restrict file permissions, use SQLite-aware backups, and protect both the database and its WAL files. Bind the service only to a trusted local interface unless it is behind a properly configured TLS reverse proxy.

The repository ignores `.env`; `stage-4/.env.example` contains placeholders only. Rotate any credential that may have been exposed. Test fixtures and fake provider tokens are not usable credentials.

## AI data handling

`POST /ai/companion` optionally uses Gemini with `GEMINI_API_KEY`, `GEMINI_MODEL`, and `GEMINI_TIMEOUT_SECONDS` configured only in the server environment. The endpoint sends a bounded question and minimized per-user summaries; descriptions and counterparty identifiers are omitted. Context and prompts are treated as untrusted data. Structured output is validated, numeric model claims are rejected, and upstream errors do not expose provider detail. Deterministic services compute authoritative values; this endpoint has no mutation tools. Review Google's current data retention and regional terms before enabling this provider for real financial data. Use `.env.example` placeholders for local setup and never log provider credentials or prompts.

## PayPal security

Sandbox checkout must remain distinct from wallet P2P payments. A browser redirect is not payment proof. Read and validate order state from PayPal before capture, use stable idempotency identifiers for retries, verify webhook signatures server-to-server, deduplicate event IDs, and reconcile uncertain outcomes from PayPal. Do not enable live credentials or live API hosts as part of this project without a separate security and product review.
